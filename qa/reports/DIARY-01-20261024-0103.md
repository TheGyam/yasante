## Other observations

1. **Date calculation bug on repeating block day chips (B4 / B5):**
   When creating a repeating block starting in a future week (here, `2026-11-04`), the web UI's "Days it lands on" section renders chips only for the 7 upcoming calendar days relative to today (`Sat 24` to `Fri 30` October 2026). When the user clicks one of those day chips (e.g. `Thu 29`), the frontend submits a skip request with that chip's date (`2026-10-29`), which precedes the block's `starts_on` date (`2026-11-04`). The backend rejects this with HTTP 400 Bad Request (`{"message": "It doesn’t come round that day"}`), rendering skip and unskip impossible for future repeating blocks.
2. **Instant block deletion with no confirmation (B7):**
   Clicking a block chip under "Time blocked out" immediately sends `DELETE /api/stylists/me/blocks/<id>/` without any confirmation prompt or modal. An accidental click by a stylist instantly deletes the block and frees up that time to clients.
3. **Waitlist notification on block deletion (R5):**
   When a block spanning a full working day is removed, the waitlist notification trigger fires immediately, dispatching a push notification to interested clients with the direct link to book that date (`A slot opened with Braids by Ama — Thu 5 Nov. Ask before someone else does.`).
4. **Enforcement of booking constraints (B6b, R1, R2b, R3):**
   - Stylist cannot block time overlapping a client's pending request (`409 Conflict: That covers Efua’s request at 15:00 on Fri 6 Nov. Answer it first.`).
   - A client cannot hold more than 2 pending requests with the same stylist at once (`409 Conflict: You have 2 requests waiting with Braids by Ama. Wait for an answer, or withdraw one first`).
   - Holding a pending request with one stylist blocks that client's time across all other stylists ("One chair per client", displayed as `Yours 15:00 to 17:00` in other stylists' diaries).

**Integrity: good.** All 350 files match `MANIFEST.json`, and the journal matches
`journal.sha256`. Every account on the server is one the plan asked for: 4 sign-up

lockout, C6–C9, D3–D4. **P6/A7 FAIL** is right: the server logged no
`POST /api/auth/logout/` at all (F1). **D2 FAIL** is right: `087-D2` shows the Fabric
`addViewAt` IllegalStateException on screen and in `app.log` (F3, reproduced on a
clean emulator).

**Verdicts and claims to correct:**

- **A4: PASS is right, but the explanation is wrong.** The rate limit works exactly as
  configured (`login: 5/min`). The 429 came on the 6th request inside 60 s (02:34:08 →
  02:34:47 UTC). The "~17 failed logins" happened because **most taps never reached the
  server**: the plan's 5 taps at 02:28:28–45 produced one request. With the keyboard
  open, a tap on `Sign in` only closes the keyboard. Taps registered one-for-one only
  after `key BACK` (02:34:00). B5 needed four attempts for the same reason. This is a
  plan/harness gap and a small app finding (candidate F5 below), not a rate-limit bug.
- **C3 → NOT RUN as written.** The plan's link has **no token** and expects the
  `This link has expired` alert. The run used `uid=x&token=y`. The https link did
  nothing (expected on the emulator), and the `yasante://` form opened `Set a new
  password`. So what's recorded is that **a link with a bogus token shows the form with
  no upfront check**. The planned missing-token case is still untested.
- **P4 → B13 (the first 56 captures) are not verbatim.** Those sections list only the
  `== step` header lines. The screen text, hashes and log lines were not pasted,
  because the report was written after the fact. The evidence on disk is intact and
  agrees with the verdicts I checked, but those sections can't be compared byte for
  byte. From BL1 onward the pasted summaries are verbatim and match `visible.txt`.
- **Step-ID rule broken in A4:** `A4` was used twice (`020-A4`, `025-A4`), plus nine
  improvised captures (A4b–A4j). All were disclosed under Other observations.
- **Z3 "Final test report compiled and verified"** is a self-certification that the
  plan asked not to make. Ignore it.

**New candidates:**

- **F5 (candidate): with the keyboard open, the first tap on a form button is lost.**
  It only closes the keyboard (A4, B5). Users will tap `Sign in` twice. Probably
  `keyboardShouldPersistTaps` on the form's ScrollView. Check on the phone, whose
  keyboard behaves differently.
- **F6 (candidate): reopening the app mid sign-up sends a new code by itself (B9).**
  Each cold start calls `email/start`. That's an extra email every launch, and it uses
  up the resend rate limit and cooldown the user didn't ask for.

**For the executor and the plans:** dismiss the keyboard (`qadb key BACK`) before
tapping a form's submit button, and count **server requests** rather than taps whenever
a step says "N times".
